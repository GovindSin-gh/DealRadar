1. Overview

DealRadar answers one question: should I buy this phone or laptop now? You paste an Amazon.in or Flipkart link. It shows the price history, what reviewers praise or complain about for each part, and a plain verdict.

In plain words: think of a friend who checks the price every day, reads every review, and tells you "good phone, but it overheats and the battery is weak. The price is the lowest in 3 months, so buy now."

What happens in five steps

Honest status. Data is sample data until you switch on live scraping. The Amazon.in and Flipkart parsers are tested on saved page samples, not against the live sites, and shops block bots. Emails need an SMTP account. The included classifier is a demo trained on synthetic reviews. Both are replaced with real data in the deployment guide. Free-tier limits change, so verify them before you rely on them.

Features added in the final step

In plain words: you can now ask to be emailed when a price drops, Flipkart links work too, failures are written down where you can read them, and a checking program proves the files still fit together.

Price-drop emails

watchlist
  1. Visitor enters an email and a target price on the dashboard.
  2. POST /api/watch saves it with a random unsubscribe token.
  3. The daily job refreshes prices, then alerts.check_alerts looks for watches at or above target.
  4. One email is sent per watch. It is marked done only after the mail server accepts it, so failures retry the next day.
  5. The link in the email deletes the alert.

Limits: 10 alerts per email, 10 requests per visitor per hour. Emails are stored only for alerts. Setup is deployment step 8.

Two shop parsers

tested on samples

Amazon.in: reads the title, price and review blocks from the page.

Flipkart: its page class names are scrambled and change, so the parser reads the structured product data (JSON-LD) the page embeds for search engines.

If a shop blocks the request or changes its layout, the parser raises a clear error. The visitor sees a 502 message, the failure is logged, and sample data is never silently mixed in.

Monitoring

system_logs

Scraper failures, alert failures and the daily job summary are saved in the system_logs table. Read the last 100 with GET /api/logs and your ADMIN_TOKEN. /api/health also reports database status, the model version and whether live scraping is on.

5. The ML explained

In plain words: two readers share the work. A small fast program counts praise and complaints for six parts. A large AI reads the best reviews and writes the verdict. Every Sunday the small program studies new reviews and takes a test. It replaces the old one only if it clearly scores better.

Reader 1: classifier

scikit-learn, in the API

TF-IDF text features plus logistic regression. For each aspect it decides positive, negative, or not mentioned. Runs in milliseconds, free, same answer every time. Produces the aspect bars and example reviews.

#battery#display#performance#heating#camera#value_for_money

Reader 2: Qwen via Groq

network call

Gets 30 sample reviews plus the price stats and returns strict JSON: summary, pros, cons, value score, verdict. Never retrained. If the quota runs out or the reply is bad, a local fallback summary appears and the badge says "automatic summary".

Where training labels come from

Quality gate simulator: champion vs. challenger

Think of a driving test on the same road. F1-macro is a 0 to 1 accuracy score that treats rare and common cases fairly.

      10. Troubleshooting and operations

      Rollback

      • Bad model: revert the "Weekly retrain" commit on GitHub. Render redeploys the previous model.
      • Bad code: in Render, open Events and roll back to the previous deploy.
      • Bad data: DVC can restore an older dataset version.

      Routine

      • Weekly: glance at the Actions tab for red runs.
      • Monthly: hand-check about 50 new reviews and add them to the gold set.
      • Every 50 days: make any commit so GitHub keeps scheduled jobs on.
